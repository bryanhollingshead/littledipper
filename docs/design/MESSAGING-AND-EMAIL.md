# Messaging and Email

> **Status: first version built** on branch `messaging` (2026-10-21): text between connected Little Dippers, inbox, outbox with retries, encrypted at rest, `messages` capability. Organization services and email are not built.

## Decided

| Decision | Date |
|---|---|
| **Invites stay as they are:** the node writes the email and the owner's own mail client sends it. Other email options will be considered later. | 2026-10-21 |
| **One inbox for everything.** Each conversation belongs to a contact, whatever the transport. | 2026-10-21 |
| **Node-to-node messaging starts minimal,** but the groundwork must support rich messaging later, both person to person and organization to person. | 2026-10-21 |
| **Organizations won't run nodes.** A business or organization gets verified, is added as a contact, and implements an API service. Managing business data is far too complex to ask them to host a Little Dipper. | 2026-10-21 |

## The foundation: messaging must not depend on running a node

Today the only parties that can talk to a node are other nodes. Organizations need to message people without running one. So the messaging protocol must be something **a service can implement on its own**, separate from the rest of what a node does.

### Who can be a contact

| Contact type | Runs a node? | Messaging transport | Status |
|---|---|---|---|
| Person (not on Little Dipper) | No | Email (later) | Exists, no messaging |
| On Little Dipper | Yes | Peer protocol | Exists |
| Organization (verified) | No, runs a **service** | Peer protocol, messaging part only | Future |
| AI | No | Scoped key / MCP | Future (question 7) |

### Protocol profiles

A party describes itself at `/.well-known/little-dipper` with a **kind** and its **capabilities** (Commandment VII):
- **A node** (`kind: "node"`) implements the full peer protocol: profile, domains, fields, links, messages.
- **A service** (`kind: "service"`, for an organization) implements only what it uses: its descriptor and signing key, and `messages`, and later perhaps `receipts`. It stores no personal data on Little Dipper's behalf.

An organization's identity is the same idea as a node's: an ID derived from its signing key. Big Dipper verification ties that key to a real organization (legal entity and domain), and the owner sees a verified badge on the contact. See [IDENTITY-VERIFICATION.md](IDENTITY-VERIFICATION.md).

### Owner control

- **Nobody can message you unless you've connected with them.** For organizations, adding them is the opt-in, and disconnecting is the unsubscribe. There's no other way for them to reach you.
- **Per-contact limits on organizations:** which message kinds they may send (receipts and service notices, but not marketing, for example), muting and rate limits.
- Organizations get the same grant model as everyone else for any data they ask for.

## Messages: data model groundwork

Designed so the minimal version doesn't need to change shape when rich features arrive.

| Field | Purpose |
|---|---|
| `id` | **Generated by the sender** and globally unique. The receiver ignores duplicates, so retries are safe. |
| `conversationId` | Groups messages into a conversation. In the first version, one conversation per contact. Named conversations and groups later. |
| `kind` | An open enum. Starts with `text`. Later: `data_request`, `share_notice`, `receipt`, `verification_request`, `read`… Clients show a generic placeholder for kinds they don't know. |
| `body` | Text for `text`. A structured payload for other kinds, each with its own schema. |
| `inReplyTo` | Optional, for threads and for replies to requests. |
| `attachments` | Empty for now. Later: references to the documents module. |
| `transport` | `peer`, `email` or `service`: how this message travelled. |
| `direction`, `status` | Outgoing: `queued` → `sent` → `delivered`, or `failed`. Incoming: `received`, then `read`. |
| `attempts`, `nextAttemptAt` | Outbox retries. |
| `createdAt`, `sentAt`, `deliveredAt`, `readAt` | Timestamps. |

On the wire: a signed envelope, as the existing peer messages already use, posted to `POST /peer/v1/messages`. The receiver's HTTP response confirms delivery. Read receipts, if they're added, are a separate message kind, and the owner can turn them off.

## Minimal first version (proposed)

- One-to-one text between connected Little Dipper contacts.
- Inbox in the admin, with one conversation per contact and an unread count in the sidebar.
- Outbox with retries using increasing delays (a few days, then `failed`).
- Messages encrypted at rest with the node key.
- The `messages` capability in the descriptor, so senders skip older nodes.
- **Built with the full data model above** (`kind`, `conversationId`, sender-generated `id`, `transport`), even though only `text` and `peer` are used at first.

## Email (later)

Not now. Recorded so it isn't lost:
- **Don't run a mail server on each node.** Delivery problems (port 25 blocked, IP blocklists, SPF/DKIM/DMARC) and abuse risk would make it the main source of support trouble for one-click installs.
- Options to consider later: an optional relay (`LD_SMTP_URL` pointing at the owner's provider), incoming email through a provider webhook (Postmark, Mailgun, SES), which is also how forwarding receipts would work, and perhaps an opt-in, rate-limited Big Dipper relay.
- In the single inbox, email conversations with non-Little Dipper contacts appear next to peer ones, marked as not end-to-end encrypted.
